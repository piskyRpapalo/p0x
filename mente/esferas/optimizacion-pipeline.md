# Optimización del pipeline en Lama.CPP para MOE

> **FOCO del Soberano (literal):** Can we apply this knowledge in our system?

## Lo nuevo

Se puede optimizar el lado MOE de Lama.CPP para modelos de 35 billones de parámetros con solo 3 billones activos por token en un entorno con 12 GB de VRAM. En el modo de decodificación, los expertos offloaded se ejecutan en la CPU utilizando RAM, sin necesidad de transferir pesos por PCIe. En el modo de prefill, se procesan miles de tokens simultáneamente y cada token requiere la carga de expertos desde la RAM hacia el GPU. El sistema de Lama.CPP realiza benchmarks antes y después de cada cambio para verificar que no hay regresión en el rendimiento. La configuración de Lama.CPP en el entorno de 12 GB de VRAM y 32 GB de RAM permite ejecutar modelos MOE con capas grandes en RAM y en GPU. La suposición inicial de que los expertos en RAM se ejecutan en CPU y los en GPU se ejecutan en GPU es parcialmente correcta y solo se aplica en decodificación. La ejecución de expertos en un sistema con CPU sería extremadamente pesada debido a que tendría que cargar todos los expertos desde RAM. Lama.CPP reduce la carga computacional al mover los pesos de los expertos desde RAM a VRAM para que el GPU los ejecute en paralelo. El bottleneck en el sistema no es el GPU, sino el bus PCIe, que tarda más tiempo en copiar datos de RAM a VRAM que en realizar cálculos reales. En un prefill pass de un modelo de 35B con UBatch 2048, se logra una tasa de 1143 tokens por segundo, que sirve como referencia para el rendimiento posterior. Fable identificó un fragmento de código inactivo que permite pinar la memoria paged, aunque no se está utilizando en la actual implementación. La opción de no usar MMAP carga el modelo en una sección de memoria privada que no es evictada por el sistema operativo. Con MM, el cargado del modelo es casi instantáneo y se siente como cero tiempo de carga. Sin mapa M, se debe cargar todo el peso en la sección privada, lo que provoca un tiempo de espera significativo para cargar o cambiar un modelo. El dead code Fable permite fijar el mapa M en memoria pagada, manteniendo el rendimiento de transferencia sin M map pero conservando las ventajas de M map como carga instantánea de modelos. El enfoque de Fable solo fija los pesos expertos, no todo el modelo, por lo que no requiere mucho espacio adicional. La base de rendimiento era de 1143 tokens por segundo en prefill, y con esta mejora se alcanza aproximadamente 1385, lo que representa un aumento del 21%. El problema de pipeline se produce porque el GPU calcula la tensión, luego ejecuta el router para obtener IDs de expertos, y mientras se copian los expertos desde RAM a VRAM, el GPU queda inactivo esperando. El tiempo de inactividad del GPU se reduce de un 41.7% a un 2.8% mediante una optimización que permite que los pesos de los expertos se carguen paralelamente al cálculo de atención. La optimización se basa en un patrón de dos canales paralelos: uno para el cálculo de atención y otro para cargar los expertos desde la RAM al GPU. Durante el cálculo de atención, se cargan todos los expertos al GPU en lugar de esperar a que el router entregue los IDs de expertos. La solución permite que el GPU esté siempre ocupado, eliminando el tiempo de inactividad durante el procesamiento de lotes. La optimización no afecta la calidad de salida, manteniendo el mismo resultado que antes de la mejora. El propio código de la optimización detecta y corrige un error antes de que sea observado por el desarrollador. El proceso de decodificación en un modelo offloaded MOE no es CPU-bound, sino que presenta un equilibrio cercano de 50% entre CPU y GPU. La especulación en decodificación, al aumentar el número de tokens anticipados, incrementa el costo de verificación debido a la necesidad de leer todos los expertos. Al aumentar el número de tokens especulados, el conjunto de expertos involucrados crece y el costo de verificación se vuelve mayor, lo que reduce la eficiencia.
