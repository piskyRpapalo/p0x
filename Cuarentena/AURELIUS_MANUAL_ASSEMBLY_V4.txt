CAPÍTULO 1: REQUISITOS PREVIOS
--------------------------------------------------------------------------------
Antes de tocar una línea de código, verifica que el entorno cumple estos
requisitos. Si alguno falla, NO continúes hasta resolverlo.

1.1 HARDWARE MÍNIMO POR PERFIL
------------------------------------------------------------

PERFIL LITE (BRONCE completo + PLATA parcial):
  - CPU: x86_64 o ARM64 (Apple Silicon, Raspberry Pi 4/5)
  - RAM: 8 GB mínimo (4 GB para SO + 4 GB para modelo 3B-7B)
  - Almacenamiento: 10 GB libres (código + modelos + datos)
  - Red: Loopback únicamente (localhost/127.0.0.1)
  - GPU: Opcional. CPU-only es suficiente para BRONCE.

PERFIL PRO (BRONCE + PLATA + ORO):
  - CPU: x86_64 multi-core (6+ cores recomendados)
  - RAM: 32 GB mínimo (16 GB para modelo 14B-32B + 16 GB para sistema)
  - Almacenamiento: 50 GB libres (múltiples modelos + FAISS + datos)
  - Red: Loopback + red privada (Tailscale o WireGuard)
  - GPU: Recomendada (CUDA o Metal). No obligatoria pero altamente deseable.

PERFIL MESH (PRO + nodos interconectados):
  - Cada nodo debe cumplir perfil PRO.
  - Red privada estable entre nodos (Tailscale o WireGuard configurado).
  - Ancho de banda: 10 Mbps mínimo entre nodos.

1.2 DEPENDENCIAS DEL SISTEMA OPERATIVO
------------------------------------------------------------

OBLIGATORIAS (sin estas, el sistema no arranca):
  - Python 3.10 o superior
  - Git (para clonado de repo y descarga de repos de evaluación)
  - Ollama (motor de inferencia local, o alternativa compatible con /api/tags)

RECOMENDADAS (mejoran experiencia pero no bloquean):
  - tmux (para skills de terminal: B.17, B.19, B.21)
  - Node.js 18+ (solo si el frontend usa build tools; vanilla HTML/JS no lo requiere)

OPCIONALES (habilitan skills específicas):

  - firejail o nsjail (para sandbox de compilación en P.19)
  - Tailscale o WireGuard (para ORO: O.03, O.04, O.05, O.11)

1.3 VERIFICACIÓN DE ENTORNO (SCRIPT DE CHECK)
------------------------------------------------------------

Ejecuta este script ANTES de clonar el repositorio. Si falla algún check,
resuélvelo antes de continuar.

```bash
#!/bin/bash
# aurelius-env-check.sh
# Script de verificación de entorno para Aurelius V4

echo '=== AURELIUS ENVIRONMENT CHECK ==='
echo ''

# Check Python
python_version=$(python3 --version 2>/dev/null | grep -oP '\d+\.\d+')
if [ -z '$python_version' ]; then
    echo '[FAIL] Python 3 no encontrado. Instala Python 3.10+')
    exit 1
fi
major=$(echo $python_version | cut -d. -f1)
minor=$(echo $python_version | cut -d. -f2)
if [ $major -lt 3 ] || [ $minor -lt 10 ]; then
    echo '[FAIL] Python $python_version es muy antiguo. Necesitas 3.10+')
    exit 1
fi
echo '[PASS] Python $python_version'

# Check Git
if ! command -v git &> /dev/null; then
    echo '[FAIL] Git no encontrado. Instala Git.'
    exit 1
fi
echo '[PASS] Git disponible'

# Check Ollama
if ! curl -s http://localhost:11434/api/tags > /dev/null 2>&1; then
    echo '[WARN] Ollama no responde en localhost:11434. Instala y arranca Ollama.'
    echo '         O configura otro endpoint compatible en config.lite.json')
else
    echo '[PASS] Ollama responde en localhost:11434'
fi

# Check RAM
ram_gb=$(python3 -c 'import psutil; print(int(psutil.virtual_memory().total / 1024**3))' 2>/dev/null || echo '0')
if [ $ram_gb -lt 8 ]; then
    echo '[WARN] RAM detectada: ${ram_gb}GB. Minimo recomendado: 8GB para LITE, 32GB para PRO'
else
    echo '[PASS] RAM detectada: ${ram_gb}GB'
fi

# Check espacio en disco
disk_gb=$(df . | tail -1 | awk '{print int($4/1024/1024)}')
if [ $disk_gb -lt 10 ]; then
    echo '[WARN] Espacio libre: ${disk_gb}GB. Minimo: 10GB para LITE, 50GB para PRO'
else
    echo '[PASS] Espacio libre: ${disk_gb}GB'
fi

# Check compiladores (opcional)
for compiler in rustc tsc go gcc; do
    if command -v $compiler &> /dev/null; then
        echo '[PASS] Compilador $compiler disponible (para P.19)'
    else
        echo '[INFO] Compilador $compiler no encontrado. Skill P.19 no estara disponible.'
    fi
done

echo ''
echo '=== ENVIRONMENT CHECK COMPLETE ==='
echo 'Si todos los checks [PASS], puedes continuar con el Capitulo 2.'
```

1.4 CLONADO DEL REPOSITORIO Y VERIFICACIÓN DE ABM
------------------------------------------------------------

Paso 1: Clonar el repositorio
  git clone https://github.com/davidmartinez/aurelius.git
  cd aurelius

Paso 2: Verificar el Aurelius Bootstrap Manifest (ABM)
  El archivo aurelius.abm debe estar en la raiz del repositorio.
  Contiene la lista de dependencias Python con sus hashes SHA-256.

  Si el archivo NO existe, el repositorio está corrupto o incompleto.
  NO instales dependencias sin el ABM.

Paso 3: Verificar hashes de dependencias
  python3 scripts/verify_abm.py

  Este script:
    a. Lee aurelius.abm
    b. Descarga cada wheel de PyPI
    c. Calcula SHA-256 del wheel descargado
    d. Compara con el hash esperado en ABM
    e. Si hay discrepancia: ABORTA y muestra error

  Si verify_abm.py falla, NO continues. Contacta a david@aurelius.software
  o verifica manualmente los hashes en https://pypi.org/project/<nombre>/

Paso 4: Instalar dependencias (solo despues de verificar ABM)
  pip install -r requirements.txt

Paso 5: Crear directorio de configuracion
  mkdir -p config/
  cp config/config.lite.example.json config/config.lite.json
  cp config/config.pro.example.json config/config.pro.json

Paso 6: Editar config.lite.json con tu endpoint de Ollama
  {
    'profile': 'LITE',
    'ollama_endpoint': 'http://localhost:11434',
    'model': 'llama3.2:3b',
    'vault_path': './sovereign_vault',
    'port': 3000
  }

Paso 7: Inicializar el vault
  python3 scripts/init_vault.py --profile LITE

  Este script crea:
    sovereign_vault/bronze/
    sovereign_vault/gold/
    sovereign_vault/worktrees/default/
    sovereign_vault/config/
    sovereign_vault/cache/

Paso 8: Generar par de claves Ed25519 para firma de Gold
  python3 scripts/generate_keys.py

  Esto genera:
    sovereign_vault/.keys/ed25519_private.pem
    sovereign_vault/.keys/ed25519_public.pem

  ADVERTENCIA: La clave privada NUNCA debe salir del dispositivo.
  Sin la clave privada, no puedes sellar en Gold ni emitir PoKs.

Paso 9: Primer arranque del servidor
  python3 server.py --profile LITE

  Si el servidor arranca sin errores y muestra:
    '[Aurelius] Perfil: LITE | Motor: SOBERANO | Modelo: llama3.2:3b'
  entonces el entorno está listo.

CAPÍTULO 3: PROTOCOLO DE INTEGRACIÓN DE NUEVA SKILL
--------------------------------------------------------------------------------
Procedimiento obligatorio para añadir una skill al catálogo. Cualquier skill
que no siga este protocolo es inválida y debe ser rechazada en auditoría.

3.1 PASO 1: VERIFICAR INVARIANTES
------------------------------------------------------------
Antes de proponer una skill nueva, responde estas 5 preguntas:

  1. ¿Esta skill viola el principio Local-first?
     -> Si requiere datos en la nube o servidor central: RECHAZAR.

  2. ¿Introduce ejecución autónoma de comandos (violación IronClaw)?
     -> Si el sistema ejecuta algo sin aprobación humana explícita: RECHAZAR.

  3. ¿Usa LLM para evaluar o juzgar (violación Honest Math)?
     -> Si el LLM decide si el usuario pasó o falló: RECHAZAR.
     -> El LLM solo redacta. Los números salen de código determinista.

  4. ¿Añade dependencia sin justificar en el ABM?
     -> Si requiere pip install <nuevo_paquete> sin justificación técnica: RECHAZAR.
     -> Justificación válida: 'FAISS es necesario para búsqueda semántica en RAG'
     -> Justificación inválida: 'Es más fácil con esta librería'

  5. ¿Expone datos personales sin salvaguarda técnica (GDPR/EU AI Act)?
     -> Si genera PII sin cifrado, sin consentimiento, o sin HRG/CEL/RTC: RECHAZAR.

  Si alguna respuesta es SÍ: la skill no entra. No negociable.

3.2 PASO 2: ANALIZAR DEPENDENCIAS EXISTENTES
------------------------------------------------------------

  a. Buscar en el Catálogo V4 (Sección B) si ya existe una skill similar.
     Usa keywords, no solo códigos. Ej: buscar 'evaluación' puede encontrar P.08.

  b. Buscar en el Anexo V4 (Parte III) si el caso límite ya fue analizado.
     No reinventar vectores de ataque ya documentados.

  c. Identificar qué skills existentes dependen de la nueva skill o viceversa.
     Usar el Mapa de Dependencias (Catálogo V4, Sección D) como referencia.

  d. Verificar que no se crea un ciclo en el DAG.
     Si A depende de B y B depende de A: arquitectura inválida.

3.3 PASO 3: ASIGNAR CÓDIGO
------------------------------------------------------------

  a. Determinar medallón:
     - ¿Requiere solo Python + JSONL + HTML/JS? -> BRONCE
     - ¿Requiere FAISS, evaluación, Gold poblado, o embeddings? -> PLATA
     - ¿Requiere criptografía, red privada, transferencia, o 32GB+ RAM? -> ORO

  b. Asignar número:
     - Buscar el último número usado en ese medallón.
     - El siguiente número disponible es el código.
     - Ej: si último BRONCE es B.27, la nueva es B.28.

  c. El código es INMUTABLE. Si la skill evoluciona, conserva su código.

3.4 PASO 4: REDACTAR SKILL EN FORMATO DEL CATÁLOGO
------------------------------------------------------------

  Usar el formato obligatorio de la Sección C del Catálogo V4:

  ---
  SKILL [CÓDIGO]: [NOMBRE]
  ---
  Medallón: [BRONCE|PLATA|ORO]
  Estado: [STABLE|BETA|DEPRECATED|MERGED|BLOQUEADA_POR_AUDITORIA]
  Descripción: [una oración de propósito]
  Mecánica: [cómo funciona paso a paso]
  Valor: [qué resuelve para el usuario]
  Requisitos técnicos: [qué se necesita implementar]
  Dependencias: [lista de códigos, no nombres]
  Invariantes aplicadas: [cuáles de la Sección A aplica]
  Puntos de fricción: [qué predice el usuario, qué recupera]
  Reglas de seguridad: [qué está prohibido hacer]
  Historial de cambios:
    - V4: [cambio actual]
  ---

  Si falta algún campo, la skill está incompleta.

3.5 PASO 5: REDACTAR CASO COMPLEJO EN EL ANEXO (si aplica)
------------------------------------------------------------

  Si la skill tiene dimensión psicológica:
    - Añadir entrada en Anexo V4, Parte I (Psicología del Diseño)
    - Incluir: teoría aplicada, efecto esperado, riesgo contrario, métrica de validación

  Si la skill genera datos estructurados:
    - Añadir schema JSON en Anexo V4, Parte II (Arquitectura de Datos)
    - Incluir: path del archivo, schema completo, clasificación PII, salvaguarda

  Si la skill tiene vectores de ataque identificables:
    - Añadir entrada en Anexo V4, Parte III (Casos Límite)
    - Incluir: caso límite, probabilidad, impacto, mitigación en V4

  Si la skill es monetizable:
    - Añadir entrada en Anexo V4, Parte IV (Modelos de Negocio)
    - Incluir: producto derivado, qué se vende, a quién, restricciones legales

3.6 PASO 6: ACTUALIZAR MAPA DE DEPENDENCIAS
------------------------------------------------------------

  a. Añadir la nueva skill al Mapa de Dependencias (Catálogo V4, Sección D).

  b. Indicar su nivel en el DAG (Nivel 0 si no tiene dependencias internas).

  c. Verificar que no introduce ciclos:
     python3 scripts/verify_dag.py

  d. Si introduce dependencias externas nuevas:
     - Añadir al ABM con hash SHA-256
     - Ejecutar verify_abm.py para confirmar

3.7 PASO 7: ACTUALIZAR RONDA DE ENSAMBLAJE
------------------------------------------------------------

  a. Determinar en qué ronda pertenece la nueva skill:
     - BRONCE fundamental -> Ronda 1
     - BRONCE extendido -> Ronda 2
     - PLATA fundamental -> Ronda 3
     - PLATA extendida -> Ronda 4
     - ORO -> Ronda 5

  b. Añadir checklist de completitud en la ronda correspondiente.

  c. Si la skill cambia el orden de implementación de otras skills,
     documentar la razón y obtener consenso de auditoría.

3.8 PASO 8: AUDITORÍA DE SEGURIDAD
------------------------------------------------------------

  Checklist de 5 preguntas de seguridad (ver Capítulo 4):

  1. ¿Rompe Local-first?
  2. ¿Rompe IronClaw?
  3. ¿Rompe Honest Math?
  4. ¿Añade dependencia sin ABM?
  5. ¿Expone PII sin salvaguarda?

  Si alguna es SÍ: volver al Paso 1.

  Adicionalmente, verificar:
  6. ¿La skill tiene tests deterministas que no dependen del LLM?
  7. ¿Los tests cubren casos límite documentados en el Anexo?
  8. ¿La skill maneja errores graceful (no crashes, no datos falsos)?

CAPÍTULO 4: CHECKLIST DE AUDITORÍA RÁPIDA
--------------------------------------------------------------------------------
5 preguntas que cualquier experto AI debe responder antes de proponer cambios.
Estas preguntas son el filtro de entrada. Si alguna falla, no se discute el cambio.

4.1 PREGUNTA 1: ¿ROMPE LOCAL-FIRST?
------------------------------------------------------------

  Criterio: Los datos del usuario nunca abandonan el nodo sin consentimiento
  explícito por entrada.

  Señales de alarma:
    - La skill requiere un servidor central para funcionar.
    - La skill sincroniza automáticamente con la nube sin preguntar.
    - La skill envía datos a un API de terceros sin advertencia clara.
    - La skill almacena datos del usuario en servidores de David.

  Preguntas de seguimiento:
    - ¿Dónde se almacenan los datos generados por esta skill?
    - ¿El usuario puede ver y borrar esos datos en cualquier momento?
    - ¿Hay algún flujo de datos que salga del dispositivo sin consentimiento?

  Veredicto: Si la skill requiere conectividad externa para su función principal,
  debe ser ORO y el usuario debe aprobar cada transmisión individualmente.

4.2 PREGUNTA 2: ¿ROMPE IRONCLAW?
------------------------------------------------------------

  Criterio: El sistema PROPONE; el humano EJECUTA y FIRMA.
  PROHIBIDA la ejecución autónoma de comandos.

  Señales de alarma:
    - La skill ejecuta un comando del usuario sin mostrarlo primero.
    - La skill modifica archivos del sistema sin confirmación.
    - La skill instala dependencias automáticamente.
    - La skill reinicia servicios sin preguntar.

  Preguntas de seguimiento:
    - ¿Esta skill ejecuta algún código del usuario o generado por modelo?
    - ¿Hay algún camino donde el sistema actúe sin aprobación humana?
    - ¿El usuario puede revisar y cancelar cualquier acción propuesta?

  Veredicto: Si hay ejecución autónoma, la skill no entra. Sin excepciones.
  La única excepción es el compilador en sandbox (P.19), que no ejecuta código
  del usuario; solo compila con flags de verificación.

4.3 PREGUNTA 3: ¿ROMPE HONEST MATH?
------------------------------------------------------------

  Criterio: Los números salen SIEMPRE de código determinista. El LLM solo redacta.
  PROHIBIDO usar LLM para evaluar, juzgar, o decidir.

  Señales de alarma:
    - El LLM decide si el usuario 'pasó' una evaluación.
    - El LLM calcula métricas de calidad de código.
    - El LLM determina si un comando es seguro.
    - El LLM asigna un score numérico a algo.

  Preguntas de seguimiento:
    - ¿Quién genera los números que esta skill presenta? ¿Código o LLM?
    - ¿Hay algún punto donde el LLM evalúa la respuesta del usuario?
    - ¿Los tests de esta skill son deterministas (mismo input = mismo output)?

  Veredicto: Si el LLM evalúa, la skill no entra. Las evaluaciones son código fijo.
  El LLM puede redactar explicaciones, generar problemas, o traducir errores.
  Pero NUNCA juzga, califica, o decide.

4.4 PREGUNTA 4: ¿AÑADE DEPENDENCIA SIN ABM?
------------------------------------------------------------

  Criterio: Toda dependencia externa debe estar en el Aurelius Bootstrap Manifest
  con hash SHA-256 verificable.

  Señales de alarma:
    - pip install <nuevo_paquete> sin justificación técnica.
    - El paquete no está en aurelius.abm.
    - El paquete es closed-source sin alternativa open-source documentada.
    - El paquete tiene vulnerabilidades conocidas (CVE) sin mitigación.

  Preguntas de seguimiento:
    - ¿Por qué esta dependencia es necesaria y no puede reemplazarse con stdlib?
    - ¿Cuál es el hash SHA-256 del wheel en PyPI?
    - ¿Hay alternativas open-source? ¿Por qué se eligió esta?
    - ¿Qué pasa si esta dependencia desaparece de PyPI mañana?

  Veredicto: Si la dependencia no está en ABM o no tiene justificación técnica,
  la skill no entra. El ABM es la línea de defensa contra supply chain attacks.

4.5 PREGUNTA 5: ¿EXPONE PII SIN SALVAGUARDA?
------------------------------------------------------------

  Criterio: Todo dato personal debe estar cifrado, con consentimiento, y con
  mecanismos de control del usuario (HRG/CEL/RTC si aplica a contexto B2B).

  Señales de alarma:
    - La skill almacena conversaciones sin cifrado.
    - La skill comparte datos con terceros sin opt-in explícito.
    - La skill genera scores evaluativos sin HRG/CEL/RTC en contexto B2B.
    - La skill expone nombres de archivos, IPs, o credenciales en logs.

  Preguntas de seguimiento:
    - ¿Qué datos personales genera esta skill?
    - ¿Cómo se clasifican según GDPR (PII, sensitive, special category)?
    - ¿Hay cifrado en reposo? ¿Y en tránsito?
    - ¿El usuario puede borrar sus datos en cualquier momento?
    - ¿Hay salvaguardas contra uso por empleadores sin consentimiento?

  Veredicto: Si la skill genera PII sin salvaguardas técnicas documentadas,
  la skill no entra. La privacidad no es un feature; es un requisito de arquitectura.

4.6 PROTOCOLO DE APLICACIÓN
------------------------------------------------------------

  Antes de proponer CUALQUIER cambio (nueva skill, modificación, o eliminación):

  1. Imprimir estas 5 preguntas.
  2. Responder cada una por escrito.
  3. Si alguna respuesta es 'Sí' o 'No estoy seguro': detenerse y corregir.
  4. Si todas las respuestas son 'No': documentar las respuestas en el commit.

  Formato de documentación en commit:
  ```
  Auditoría rápida para [CÓDIGO]:
  1. Local-first: NO ROMPE. Datos almacenados en bronze/[skill]/ local.
  2. IronClaw: NO ROMPE. Sistema propone; usuario aprueba.
  3. Honest Math: NO ROMPE. Métricas de parser AST determinista.
  4. ABM: NO AÑADE. Sin dependencias nuevas.
  5. PII: NO EXPONE. Solo métricas agregadas, sin datos identificables.
  ```

5.1 PROTOCOLO GENERAL DE DEBUGGING
------------------------------------------------------------

  Paso 1: Identificar la skill afectada por el código de error o traceback.

  Paso 2: Revisar el checklist de completitud de esa skill en el Manual V4.
          ¿Algún item no está marcado? Esa es probablemente la causa.

  Paso 3: Revisar el Anexo V4, Parte III (Casos Límite) para esa skill.
          ¿El error coincide con un vector de ataque documentado?

  Paso 4: Revisar logs en sovereign_vault/logs/ (append-only, human-legibles).

  Paso 5: Si el error persiste, ejecutar tests específicos:
          python3 -m pytest tests/ronda[N]/test_[skill_code].py -v

  Paso 6: Si los tests pasan pero el error persiste en producción:
          - Diferencia entre entorno de test y producción (RAM, SO, dependencias).
          - Condición de carrera o estado compartido.
          - Datos corruptos en Bronce/Gold (verificar hashes de cadena).

  Paso 7: Documentar la solución en este capítulo para futuros desarrolladores.
