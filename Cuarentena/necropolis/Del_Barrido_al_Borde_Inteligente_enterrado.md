## Fundamentos Arquitectónicos: Implementación de la Arquitectura Medallion

La implementación de la arquitectura Medallion representa un cambio fundamental en la gestión de datos del ecosistema P0X, pasando de un modelo reactivo a uno proactivo y estructurado. Esta arquitectura no es meramente una preferencia técnica; es la respuesta directa al problema documentado de la deriva y la falta de un plan cohesivo que ha impedido la expansión funcional . La doctrina `equipo-ai-loop-p0x.md` ya sentó las bases para este enfoque al priorizar la especificación sobre la construcción y la ejecución sobre la deliberación . La arquitectura Medallion formaliza este principio en una capa de datos diseñada para gestionar la creciente complejidad de los datos, desde los sensores físicos hasta los logs de agentes. El objetivo es crear un sistema donde cada dato tenga un estado definido y predecible, desde su origen crudo hasta su uso final en aplicaciones de negocio o análisis. Este fundamento es crucial antes de proceder a cualquier otra tarea de desarrollo o integración.

La arquitectura Medallion organiza los datos en tres capas distintas y progresivamente refinadas, cada una con un propósito y un conjunto de reglas claras [[39](https://www.useready.com/thought-leadership/transforming-data-swamps-to-ai-ready-assets-executing-the-databricks-medallion-architecture-for-business-value), [40](https://www.actian.com/blog/data-architecture/rethinking-the-medallion-architecture-for-modern-data-platforms/)].

El primer paso para materializar esta arquitectura es definir los esquemas de datos para cada producto y servicio del ecosistema P0X. Antes de construir, se deben especificar. Por ejemplo, para el sensor BME680, el esquema de la capa Bronze podría definir campos explícitos para temperatura, humedad, presión y gas, junto con metadatos de timestamp e ID del dispositivo [[33](https://botland.store/grove-weather-sensors/15330-grove-temperature-humidity-pressure-and-gas-sensor-bme680-i2cspi-5903351246644.html), [309](https://www.youtube.com/watch?v=zIhfPDmX-p0)]. Para los datos de impresión 3D, los esquemas podrían definir parámetros de trabajo y estado del mismo [[1]([URL_REDACTADA] Integral para Aurelius Evolucionado_ Orquestación de Agentes en Edge con LongHorizon Harness y BigBang v1(2).md?[TOKEN_REDACTADO])]. Estos artefactos deben ser versionados en disco para servir como contrato entre los diferentes subsistemas del ecosistema.

En este marco, Aurelius asume el rol de Filtro Edge determinista, convirtiéndose en la primera línea de defensa y calidad de los datos [[1]([URL_REDACTADA] Integral para Aurelius Evolucionado_ Orquestación de Agentes en Edge con LongHorizon Harness y BigBang v1(2).md?[TOKEN_REDACTADO])]. Su función principal es interceptar todos los datos entrantes antes de que lleguen a la capa Bronze, actuando como un middleware que filtra el ruido de telemetría y aplica un parsing estructurado [[8](https://www.mdpi.com/2079-9268/15/4/60), [51](https://www.flagsmith.com/feature-flag-bank-financial-services)]. Las cargas útiles que no cumplan con los esquemas de validación previamente definidos deben ser descartadas de forma segura, evitando así que datos corruptos o malformados comprometan toda la cadena de procesamiento posterior. Este proceso no solo mejora la calidad de los datos, sino que también reduce drásticamente la sobrecarga de procesamiento en el núcleo del sistema y la necesidad de transmitir grandes volúmenes de datos innecesarios, lo cual es especialmente relevante para la filosofía de soberanía local-first y eficiencia energética [[3](https://www.sciencedirect.com/science/article/pii/S2542660523002536), [72](https://medium.com/accredian/tinyml-ai-at-the-edge-f32369bc732b)]. La capacidad de Aurelius para identificar y comunicarse con los cuatro dispositivos hardware funcionales (ESP32 atomlite m5stack con sensores axl345, apklvsr, bme680, y cámara) es la prueba de concepto inicial y crítica para validar que este rol de filtro Edge es viable en el entorno físico actual . La conexión exitosa con estos sensores demuestra que la interfaz entre el mundo digital y el físico es sólida y predecible, un prerrequisito indispensable para la fiabilidad de toda la arquitectura.

## Protocolo de Auditoría y Limpieza del Sistema P0X

Una vez establecidos los fundamentos arquitectónicos, el siguiente paso es purgar la base de código de software residual y reducir la complejidad inherente acumulada. Este proceso no es destructivo, sino reconstructivo, y debe seguir un protocolo riguroso para garantizar que cada modificación sea justificable, reversible y aumente la mantenibilidad del sistema. El objetivo es transformar el código de una colección de ideas aisladas a un sistema coherente y dirigido por principios. El rol de Claude Cowork en este proceso es actuar como un supervisor disciplinado, siguiendo un manual de archivo que guíe tanto su propio comportamiento como el de Claude Code cuando sea necesario.

El protocolo se divide en dos fases principales: auditoría y acción. La fase de auditoría comienza con una detección exhaustiva de elementos residuales. Esto incluye scripts huérfanos que no son invocados por otros componentes, dependencias de bibliotecas que ya no se utilizan en el código fuente, configuraciones obsoletas que han sido reemplazadas por versiones más nuevas, y archivos temporales o de registro que quedaron permanentemente después de pruebas o depuraciones [[65](https://www.youtube.com/watch?v=EvszZoXxPH8), [148](https://esp32.com/viewtopic.php?t=13908)]. Además, se debe buscar activamente patrones de sobreingeniería, abstracciones innecesarias que añaden complejidad sin proporcionar un beneficio claro, y duplicación de lógica en múltiples partes del código base [[68](https://www.sciencedirect.com/science/article/abs/pii/S0167739X25004881), [242](https://www.reddit.com/r/esp32/comments/1tvbg4n/codex_for_esp32/)]. La herramienta clave para esta tarea es Claude Code, cuya capacidad Opus 5 puede ayudar a detectar patrones sutiles que un humano podría pasar por alto [[86](https://www.reddit.com/r/ClaudeAI/comments/1s1o3t8/i_built_a_react_framework_with_48_claude_code/)]. Sin embargo, la interpretación y la decisión final siempre recaen en el Soberano, que valida las propuestas generadas por el agente.

Una vez completada la auditoría, se genera una Matriz de Auditoría y Limpieza. Esta matriz es el entregable central de la fase de auditoría y debe ser un documento versionado en disco. Cada fila en la matriz corresponde a un componente del sistema (archivo, función, módulo) y debe contener las siguientes columnas:
*   **Componente:** Nombre del archivo o unidad de código.
*   **Acción Propuesta:** Una de las siguientes opciones: `ELIMINAR`, `REFACTORIZAR`, `CONSERVAR`. La elección debe estar estrictamente justificada.
*   **Justificación Técnica:** Un párrafo que explique por qué se propone esa acción, basándose en métricas de rendimiento, simplicidad, o acoplamiento.
*   **Coste/Beneficio Estimado:** Una estimación del tiempo requerido para la acción frente al beneficio obtenido en términos de mantenibilidad, velocidad o seguridad.
*   **Plan de Reversión/Respaldo:** Si la acción propuesta es `ELIMINAR`, se debe incluir un plan claro sobre cómo revertir el cambio si resultara perjudicial, como un comando de copia de seguridad o un punto de restauración en el sistema de control de versiones.

Este formato obliga a que cada propuesta sea concreta, verificable y documentada, cumpliendo con la doctrina que exige que todo trabajo dejado en disco sea trazable y auditable [[21](https://www.augmentcode.com/guides/claude-agent-sdk-agent-loops-tool-calls)]. El Soberano firma la decisión final, aceptando o modificando las propuestas de la matriz. Solo después de esta validación se autoriza la ejecución. Durante la fase de acción, Claude Cowork debe operar bajo estrictas restricciones: prohibida la introducción de nuevos frameworks o dependencias externas no justificadas, y manteniendo el determinismo en la manipulación de estados y datos [[1]([URL_REDACTADA] Integral para Aurelius Evolucionado_ Orquestación de Agentes en Edge con LongHorizon Harness y BigBang v1(2).md?[TOKEN_REDACTADO])]. Toda propuesta de borrado debe ir acompañada de su correspondiente plan de reversión o backup previo, asegurando que el sistema nunca quede en un estado indefinido o irreparable [[1]([URL_REDACTADA] Integral para Aurelius Evolucionado_ Orquestación de Agentes en Edge con LongHorizon Harness y BigBang v1(2).md?[TOKEN_REDACTADO])]. Este protocolo transforma la limpieza de un acto de destrucción potencial a una mejora estructural disciplinada y transparente.

## Instrucciones Operativas para Claude Cowork y Claude Code

Para que Claude Cowork y Claude Code sean herramientas productivas, el Soberano debe seguir un manual de explotación operativa que maximice su potencial y minimice los riesgos de malentendidos o acciones no deseadas. Este manual, a ser posible versionado como un archivo `MANUAL_COWORK.md` en la raíz del proyecto, sirve como una guía de archivo para el Soberano y como una referencia para el propio Cowork. Sus principios se derivan directamente de la doctrina `equipo-ai-loop-p0x.md` y de las mejores prácticas de interacción con agentes de IA avanzados [[64](https://aman.ai/primers/ai/claude-code/), [134](https://lawrencewu.net/posts/2026-03-10-ai-tutorial/)].

El primer principio fundamental es la **Inyección Compacta de Contexto**. En lugar de proporcionar a Claude Code volcados masivos de código fuente sin procesar, lo cual puede saturar su ventana de contexto y generar "alucinaciones" [[64](https://aman.ai/primers/ai/claude-code/)], el Soberano debe inyectarle contextos compactos y relevantes. Esto implica proporcionar índices de arquitectura, diagramas de estructura de directorios, manifiestos de esquemas de datos (como JSON Schema) y listas de variables de entorno relevantes [[64](https://aman.ai/primers/ai/claude-code/)]. El objetivo es dar al agente una comprensión de alto nivel del sistema antes de sumergirlo en detalles de grano fino. Esto se complementa con la **Gestión de Contexto Continuo**, donde el Soberano agrupa tareas relacionadas por dominio funcional (por ejemplo, "trabajar en el subsistema de hardware", "optimizar el almacenamiento de datos", "depurar el módulo de agentes") para evitar la degradación de la atención y la confusión entre dominios [[64](https://aman.ai/primers/ai/claude-code/)].

El segundo principio es un **Protocolo de Interacción Estructurado**, que refleja el ciclo `Soberano → Preceptor → Ejecutor` definido en la doctrina. El Soberano debe seguir tres fases claras al delegar una tarea:
1.  **Fase 1: Planteamiento de Requerimiento.** El Soberano define las restricciones de alto nivel y el objetivo técnico, pero no imponga la solución sintáctica. Por ejemplo, en lugar de decir "usa MicroPython para leer el sensor I2C", se debe decir "implementa la lectura de datos del sensor ADXL345 a través del bus I2C en el firmware del ESP32".
2.  **Fase 2: Deliberación Estratégica.** Claude Cowork debe analizar los vectores de fallo, evaluar las dependencias dentro del clúster y proponer un plan de acción estructurado. Este plan debe incluir una secuencia de pasos, los archivos involucrados y los posibles puntos de error.
3.  **Fase 3: Generación de Directivas.** Una vez que el Soberano aprueba el plan estratégico, Claude Cowork redacta los prompts o especificaciones técnicas de grano fino, orientadas a la ejecución en Claude Code. Estos prompts deben ser autónomos, con todo el contexto necesario para que Claude Code pueda ejecutarlos sin intervención adicional del Soberano durante su ejecución.

Finalmente, el manual debe guiar al Soberano sobre cuándo y cómo delegar tareas a Claude Code. Después de que Claude Cowork haya realizado un barrido inicial y generado una Matriz de Auditoría, debe ser capaz de identificar qué tareas pueden ser delegadas. El protocolo de delegación debe ser:
*   **Verificación Primero:** El Soberano debe verificar que Claude Code está trabajando con datos reales y no inventando información. Esto se logra pidiéndole que declare su incertidumbre explícitamente cuando algo no está claro.
*   **Propuestas Verificables:** Cada propuesta de Claude Code para una tarea de limpieza debe incluir una justificación técnica, un coste/beneficio estimado y un plan de reversión. El Soberano no debe delegar la acción hasta que revise y firme esta propuesta.
*   **Gestión de Errores:** El Soberano debe instruir a Claude Code sobre cómo manejar los errores. Por ejemplo, "si un test falla, detén la ejecución y reporta el resultado. No continúes automáticamente".

Al seguir estas instrucciones, el Soberano pasa de ser un simple prompter a un diseñador de sistemas de agentes, guiando a Claude Cowork y Claude Code para que trabajen de manera coordinada y disciplinada, maximizando la eficiencia y la calidad del resultado final [[62](https://www.facebook.com/groups/vibecodinglife/posts/2006387959949731/), [63](https://alirezarezvani.medium.com/how-to-build-claude-code-agents-from-scratch-the-10-step-framework-i-actually-use-in-production-6f6a358f4f8c)].

## Integración de Datos del ESP32 en el Dashboard v2

La preparación del dashboard v2 debe seguir una secuencia operativa estricta y disciplinada, diseñada para construir una interfaz de usuario robusta y fiable sobre una base de datos sólida. Intentar pulir la parte visual antes de asegurar la fluidez de los datos es un error común que conduce a la acumulación de deuda técnica y a frustración futura. La secuencia recomendada es la siguiente:

1.  **Establecer Primero la Estructura Modular:** Antes de escribir una sola línea de código para el dashboard, se debe haber completado la fase de fundación arquitectónica. Esto significa que los esquemas de datos para las capas Bronze, Silver y Gold están definidos y que Aurelius está funcionando como un filtro Edge en el entorno de desarrollo. El dashboard debe conectarse a esta infraestructura de datos estructurada desde el principio, no a archivos JSON sueltos o endpoints improvisados.

2.  **Conectar Segundo los Datos que ya Funcionan:** El siguiente paso es conectar los datos que ya están disponibles y funcionales. En el caso del proyecto P0X, esto implica anclar la interfaz de usuario del dashboard a los datos existentes de la planta de tomate cherry (foto, observaciones, etc.) . Este paso es crucial porque demuestra rápidamente el valor del sistema y proporciona un banco de pruebas funcional para el pipeline de datos. El objetivo es que el dashboard muestre datos reales provenientes de las capas Silver y Gold, validando así que la cadena de ingestión, limpieza y agregación funciona correctamente.

3.  **Abordar Tercero los Componentes Rotos:** Con la estructura y los datos funcionales establecidos, el foco se desplaza hacia los componentes que no están funcionando. En este caso, el principal componente roto es la conexión de los datos en tiempo real del ESP32. Este paso debe realizarse de manera sistemática:
    *   **Validación de Comunicación:** Primero, se debe confirmar que Aurelius puede identificar y comunicarse con los sensores ESP32 (axl345, bme680, etc.). Esto puede hacerse mediante un script de diagnóstico simple que solicite lecturas a los sensores a través de los buses I2C o SPI correctos [[137](https://www.arduinolibraries.info/categories/sensors), [144](https://www.engineersgarage.com/micropython-i2c-protocol-in-esp8266-and-esp3/)].
    *   **Definición de Esquemas de Dato:** Se debe definir el esquema de datos para los datos del ESP32 en la capa Bronze, asegurando que los tipos de dato (ej. float para temperatura, int para aceleración) sean consistentes.
    *   **Implementación del Pipeline:** Se debe implementar el pipeline de datos para que los datos del ESP32 fluyan a través de Aurelius (filtro Edge), hacia la capa Bronze, y luego sean transformados en la capa Silver para su consumo por el dashboard. Para ello, se pueden utilizar métodos como MQTT para la transmisión de datos en tiempo real desde el ESP32 hacia un backend que los procese y los almacene [[153](https://www.youtube.com/watch?v=HQ-66qUKp8I&vl=en-US), [154](https://www.youtube.com/watch?v=n1FsyFkIPac)].

4.  **Pulido Visual Finalmente:** Solo después de que la estructura de datos esté completamente estable y los datos del ESP32 fluyan de manera consistente, el Soberano puede dar la orden explícita para proceder con el pulido de los aspectos visuales. Esta etapa se centrará en mejorar la presentación de los datos, añadir widgets adicionales, y optimizar la experiencia de usuario, sabiendo que la base subyacente es robusta y confiable.

Esta secuencia estricta garantiza que el dashboard v2 no sea una pantalla bonita sobre un vacío funcional. Al construir sobre la arquitectura Medallion, se crea un sistema escalable donde la adición de nuevos sensores o fuentes de datos será un proceso repetible y predecible, en lugar de una crisis de integración cada vez que se introduce nueva tecnología. La filosofía de "nueve módulos canon, cero usables" subraya la importancia crítica de seguir este orden para pasar de la teoría a la práctica .

## Síntesis Estratégica y Plan de Acción Secuencial

La guía estructurada para el ecosistema P0X no es una lista de tareas, sino un plan estratégico para transformar un conjunto de prototipos funcionales en un sistema coherente, mantenible y escalable. La ejecución exitosa de este plan depende de la disciplina para seguir el ciclo de diseño-validación-ejecución y de la capacidad de traducir la visión estratégica en artefactos técnicos concretos y accionables. La doctrina `equipo-ai-loop-p0x.md` no es un obstáculo, sino el andamiaje que permite esta transformación, proporcionando las reglas para una colaboración efectiva entre el Soberano, el Preceptor (Claude App) y el Ejecutor (Claude Code).

A continuación, se presenta un plan de acción secuencial que sintetiza los hallazgos de este informe en una hoja de ruta ejecutable:

**Fase 1: Fundación Arquitectónica (Rol del Preceptor/Claude App)**

*   **Entregable 1: Guía de Requisitos de Éxito y Recopilación de Datos.** El Preceptor debe generar un documento markdown que defina qué significa "éxito" para cada producto del ecosistema (Aurelius, Hexelion, CineK, L'Herbier). Debe incluir datos mínimos necesarios, dependencias y criterios verificables [[1]([URL_REDACTADA] Integral para Aurelius Evolucionado_ Orquestación de Agentes en Edge con LongHorizon Harness y BigBang v1(2).md?[TOKEN_REDACTADO])].
*   **Entregable 2: Manual de Explotación Operativa para Claude Cowork.** Basado en este informe, el Preceptor debe crear un manual que enseñe al Soberano a maximizar la ventana de entendimiento de Cowork, cubriendo la inyección de contexto compacta, la gestión de dominios y el protocolo de interacción estructurado [[64](https://aman.ai/primers/ai/claude-code/), [134](https://lawrencewu.net/posts/2026-03-10-ai-tutorial/)].
*   **Entregable 3: Prompt de Misión para Análisis y Limpieza.** El Preceptor debe redactar el prompt completo para Claude Code, detallando las directrices de auditoría, la matriz de entrega y las restricciones operativas [[1]([URL_REDACTADA] Integral para Aurelius Evolucionado_ Orquestación de Agentes en Edge con LongHorizon Harness y BigBang v1(2).md?[TOKEN_REDACTADO])].

**Fase 2: Construcción y Limpieza (Rol del Soberano y Ejecutor)**

*   **Acción 1: Establecer Estructura Medallion.** Se implementan los esquemas de datos para las capas Bronze, Silver y Gold. Se configura y valida el rol de Aurelius como Filtro Edge.
*   **Acción 2: Conectar Datos Funcionales.** El dashboard v2 se ancla a los datos existentes (ej. planta de tomate) para validar el pipeline de datos.
*   **Acción 3: Abordar Componentes Rotos.** Se realiza el trabajo sistemático para conectar los datos del ESP32, comenzando por la comunicación física y terminando con la implementación del pipeline de datos completo.

**Fase 4: Refinamiento y Expansión (Rol del Soberano)**

*   **Acción 1: Pulido Visual.** Una vez que la base de datos y el pipeline estén sólidos, se da la orden explícita para el pulido de la interfaz de usuario del dashboard.
*   **Acción 2: Considerar Extensiones.** Con una base arquitectónica robusta, se pueden considerar extensiones futuras como la creación de una mesh de nodos o la implementación de características multiusuario, siempre bajo el prisma de la soberanía y la simplicidad.

Este plan de acción secuencial garantiza que cada decisión esté fundamentada, cada acción esté justificada y cada resultado esté registrado, cumpliendo plenamente con la doctrina y transformando el ecosistema P0X en un sistema verdaderamente integrado y potente.
