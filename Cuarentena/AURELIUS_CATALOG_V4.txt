SECCIÓN A: CONTRATO ARQUITECTÓNICO
--------------------------------------------------------------------------------
Aplicables a TODAS las skills. Inmutables sin consenso de auditoría.

A.1 PRINCIPIOS NO NEGOCIABLES
    1. Local-first: Los datos del usuario nunca abandonan el nodo sin
       consentimiento explícito por entrada.
    2. IronClaw: El sistema PROPONE; el humano EJECUTA y FIRMA.
       Prohibida la ejecución autónoma de comandos.
    3. Honest Math: Los números salen SIEMPRE de código determinista
       (parser AST, regex, calculadoras fijas). El LLM solo redacta.
    4. Sin eval/exec/subprocess con texto generado por modelo o usuario.
    5. CERO direcciones IP, nombres de host o credenciales en código o
       configuración versionada.
    6. Toda fricción debe ser PREDICCIÓN o RECUPERACIÓN. Si solo impone
       coste, no entra.
    7. Portapapeles Soberano: Sin botón de copiar; selección manual obligatoria.
    8. Command Guard: Parser determinista (regex/AST). NUNCA el LLM audita
       seguridad.
    9. Sin dependencias nuevas sin justificar en ABM (Aurelius Bootstrap Manifest).

A.2 DEFINICIÓN DE MEDALLONES
    BRONCE  → Disponible en LITE (8 GB RAM). Barrera cero. Pedagogía pura.
              Sin FAISS, sin criptografía, sin red privada. Solo Python,
              JSONL, HTML/JS vanilla, y el modelo que elija el usuario.
    PLATA   → Requiere PRO o progreso en misiones. Añade persistencia estructurada,
              evaluación, FAISS, Gold poblado, o embeddings. No requiere red ni
              criptografía de infraestructura.
    ORO     → Requiere PRO + infraestructura avanzada: criptografía (Ed25519,
              AES-256-GCM), red privada (Tailscale), transferencia entre nodos,
              Mesh, o 32 GB+ RAM para enjambres grandes.

A.3 REGLAS DE DEPENDENCIAS ENTRE MEDALLONES
    - PLATA puede depender de BRONCE (no al revés).
    - ORO puede depender de PLATA y BRONCE (no al revés).
    - Una skill BRONCE NUNCA puede requerir una skill PLATA u ORO.
    - Las dependencias entre skills del mismo medallón deben formar un DAG
      (grafo acíclico dirigido). Ciclos = arquitectura inválida.

A.4 PROTOCOLO DE NOMENCLATURA DE SKILLS
    Formato: [MEDALLÓN].[NÚMERO] → Ej: B.18, P.08, O.11
    - Código único inmutable. Si una skill evoluciona, conserva su código.
    - Si una skill se fusiona, su código pasa a DEPRECATED (Sección E).
    - Si una skill se divide, la original se marca DEPRECATED y las nuevas
      reciben códigos siguientes disponibles.
    - Numeración por medallón: BRONCE 1-99, PLATA 1-99, ORO 1-99.

A.5 PROTOCOLO DE ESTADOS DE SKILL
    STABLE        → Implementada, auditada, sin hallazgos críticos abiertos.
    BETA          → Implementada, en período de observación.
    DEPRECATED    → Fusionada o reemplazada. No se implementan nuevas.
    MERGED        → Absorbida por otra skill. Ver Sección E.
    BLOQUEADA_POR_AUDITORIA → Hallazgo crítico sin corregir. No implementar.

A.6 PROTOCOLO DE DATOS TEMPORALES (post-auditoría V3 → V4)
    - Reemplazo de timestamp puro por Hybrid Logical Clock (HLC):
      {physical: unix_ms, logical: counter}
    - Toda entrada Gold debe incluir HLC, no solo timestamp.
    - Resolución de conflictos: HLC mayor gana. Empate → hash contenido.

A.7 PROTOCOLO DE EVALUACIÓN (post-auditoría V3 → V4)
    - Temporal Binding: Cada sesión de evaluación usa rubrica perturbada
      por nonce derivado de Gold_tip + session_timestamp + topic.
    - Commitment Protocol: Toda predicción requiere commit SHA-256 antes
      de revelar el resultado real.
    - Burst Detection: Reemplazo de umbral estático por análisis de varianza
      temporal en métricas de evaluación.

A.8 PROTOCOLO DE MESH Y REPUTACIÓN (post-auditoría V3 → V4)
    - Challenge-Response Determinista: PoK-G requiere Proof of Useful Work
      con nonce derivado de cadena Gold.
    - Slashing Ledger local: 3 PoK-D verificados contra un nodo = blacklist
      local por 30 días.
    - Stake Temporal: Ofertar servicios en Mesh requiere bloquear PoKs propios.

A.9 PROTOCOLO DE ARRANQUE DE CONFIANZA (post-auditoría V3 → V4)
    - ABM (Aurelius Bootstrap Manifest): Lista de dependencias con hashes
      SHA-256 exactos. El servidor NO arranca si un hash no coincide.
    - Alternativa soberana a Tailscale: WireGuard (open-source) documentada.

A.10 PROTOCOLO DE RESPONSABILIDAD ALGORÍTMICA (post-auditoría V3 → V4)
    - Human Review Gate (HRG): Output de scoring cognitivo requiere validación
      humana antes de ser accionable por terceros.
    - Counterfactual Explainability Layer (CEL): Explicaciones deterministas
      obligatorias para todo score.
    - Right to Contest Button (RTC): Botón técnico de impugnación inmutable
      en Gold para todo output evaluativo.

SKILL B.01: PERFILES DE CONFIGURACIÓN (PRO / LITE)
---
Medallón: BRONCE
Estado: STABLE
Descripción: El servidor acepta --perfil con dos valores. El perfil NO fija el
  modelo; fija el contrato de recursos esperados (RAM mínima, contexto), la
  interfaz de escucha (loopback para LITE, red privada configurable para PRO),
  y qué capacidades se declaran disponibles.
Mecánica:
  1. Al arrancar, el servidor lee el perfil de un argumento CLI.
  2. Carga config.lite.json o config.pro.json (no versionados; ejemplos sí).
  3. El perfil expone en /api/capabilities qué skills están disponibles.
  4. El contrato es MEDIDO, no declarado: RAM y contexto se verifican en runtime.
Valor: Un solo código, dos contratos honestos. LITE es honesto con hardware
  modesto; PRO aprovecha el nodo soberano sin mentir al clonador.
Requisitos técnicos: Argumento CLI en el servidor. Dos archivos de ejemplo de
  configuración. Parser de JSON. Verificación de RAM con psutil.
Dependencias: Ninguna nueva.
Invariantes aplicadas: A.1(4), A.1(5), A.1(9)
Puntos de fricción: Ninguno. Esta skill es infraestructura transparente.
Reglas de seguridad: Ningún perfil puede prometer capacidades que el hardware
  no pueda cumplir. Si la medición falla, el servidor arranca en modo degradado
  con advertencia explícita.
Historial de cambios:
  - V3: Versión original.
  - V4: Añadida verificación de medición runtime (no solo declaración).

SKILL B.02: DECLARACIÓN HONESTA DEL MOTOR
---
Medallón: BRONCE
Estado: STABLE
Descripción: Al arrancar, el servidor consulta al motor de inferencia qué modelo
  tiene cargado, su ventana de contexto, y su ubicación. Expone tres estados
  derivados del endpoint configurado: SOBERANO, DELEGADO, HUESPED.
Mecánica:
  1. GET al endpoint /api/tags de Ollama (o equivalente).
  2. Si no responde, valor = NO_DATA; nunca supuesto.
  3. Clasificación de topología por hostname en URL:
     localhost/127.0.0.1 → SOBERANO
     IP privada (10.x, 192.168.x, 172.16-31.x) → DELEGADO
     todo lo demás → HUESPED
  4. Visible en UI de forma permanente, no en menú oculto.
Valor: El usuario sabe siempre dónde corre su pensamiento. En modo HUESPED,
  el sistema activa protecciones automáticas (Gold offline, Templo Guard).
Requisitos técnicos: Petición HTTP al endpoint de modelos. Parser de URL para
  clasificación de red. Exposición en endpoint de estado y UI.
Dependencias: Ninguna nueva.
Invariantes aplicadas: A.1(1), A.1(5), A.1(7)
Puntos de fricción: Ninguno. Transparencia continua como andamiaje emocional.
Reglas de seguridad: La clasificación debe ser determinista, no heurística.
  Un error de clasificación (HUESPED como SOBERANO) es un fallo crítico de seguridad.
Historial de cambios:
  - V3: Versión original.
  - V4: Sin cambios. Auditada y confirmada STABLE.

SKILL B.04: HONEST MATH
---
Medallón: BRONCE
Estado: STABLE
Descripción: Capa de servicio universal de verdad numérica. PROHIBIDO ejecutar
  código generado por el modelo. Dos mecanismos: (a) evaluador de expresiones
  aritméticas con whitelist estricta de nodos AST; (b) calculadoras fijas
  pre-escritas por el desarrollador para infraestructura (VRAM, tokens, energía).
Mecánica:
  1. Cuando el usuario pregunta algo numérico, el modelo identifica qué
     calculadora aplica y con qué argumentos.
  2. El backend ejecuta la calculadora correspondiente.
  3. Si ninguna aplica, responde NO_DATA y explica por qué.
  4. La UI muestra claramente 'Calculado con [fórmula]' vs 'Generado por el modelo'.
  5. Parser AST con whitelist: solo nodos numéricos, +, -, *, /, **, paréntesis.
     Todo lo demás se rechaza en parseo.
Valor: Cero alucinación numérica en infraestructura crítica. El LLM nunca escribe
  código ejecutable. Es la vulnerabilidad #1 que Aurelius enseña a evitar,
  aplicada a sí mismo.
Requisitos técnicos: Parser AST en Python puro (ast module). Whitelist de nodos.
  Calculadoras fijas en módulo separado. Tests obligatorios.
Dependencias: Ninguna nueva (ast es stdlib).
Invariantes aplicadas: A.1(3), A.1(4), A.1(8)
Puntos de fricción: Ninguno. Transparencia numérica como pedagogía encubierta.
Reglas de seguridad: PROHIBIDO eval/exec/subprocess. Cada calculadora debe tener
  tests deterministas exhaustivos. Un bug en calculadora = responsabilidad del
  desarrollador, no 'opinión de IA'.
Historial de cambios:
  - V3: Versión original.
  - V4: Sin cambios. Auditada y confirmada STABLE. Base del Commitment Engine.

SKILL B.06: COMMAND GUARD (FIREWALL COGNITIVO)
---
Medallón: BRONCE
Estado: STABLE
Descripción: El LLM NO audita comandos. Es un parser determinista en backend
  (regex + lista negra de patrones) que corre sin LLM. Si detecta patrón
  peligroso, muestra advertencia con explicación.
Mecánica:
  1. Todo texto que parece comando (bloques <code> con clase shell/bash/sh)
     pasa por el parser antes de renderizarse.
  2. Parser usa regex y lista negra fija en archivo de configuración versionada.
  3. Si hay coincidencia: bloque envuelto en advertencia visual (rojo, icono).
  4. El modelo genera explicación educativa alrededor (solo redacción, no decisión).
  5. El usuario decide si copiar o no.
Valor: La seguridad no depende de la benevolencia del modelo. Parser determinista,
  no suposición lingüística. Protege contra alucinaciones y prompts de ingeniería social.
Requisitos técnicos: Regex en Python. Lista negra en archivo de configuración
  versionada. Pipeline de renderizado de bloques de código.
Dependencias: Ninguna nueva.
Invariantes aplicadas: A.1(3), A.1(4), A.1(8)
Puntos de fricción: Ninguno. El parser elimina ansiedad de falsos positivos.
Reglas de seguridad: Lista negra en archivo versionado (YAML/JSON), no en código.
  Tests de regresión obligatorios. No prometer '100% seguro'; documentar alcance.
Historial de cambios:
  - V3: Versión original.
  - V4: Sin cambios. Auditada y confirmada STABLE. Base de Command Guard CI/CD.

SKILL B.07: CENTINELA DE HARDWARE
---
Medallón: BRONCE
Estado: STABLE
Descripción: Monitoreo de sensores (temperatura, RAM). Solo predice y advierte,
  nunca actúa (IronClaw). Cambia el Orbe a danger y prop comando de mitigación.
Mecánica:

  2. psutil para RAM/CPU; /sys/class/thermal en Linux; equivalentes en Mac/Windows.

  4. Propone comando de mitigación pero NUNCA lo ejecuta.
  5. Sliding window de últimos 12 puntos (5s × 12 = 60s) para calcular tendencia.
Valor: Convierte mantenimiento pasivo en micro-examen de física del cómputo.
Requisitos técnicos: psutil. Lectura de sensores térmicos del SO.
Dependencias: B.03
Invariantes aplicadas: A.1(2), A.1(3)
Puntos de fricción: Predicción activa antes de advertencia ('¿qué ocurrirá en 60s?').
Reglas de seguridad: Incluir cláusula 'sin garantía de predicción'. El sistema
  es asistente, no control de temperatura certificado.
Historial de cambios:
  - V3: Versión original.
  - V4: Añadido sliding window de tendencia (derivada) para predicción.

Medallón: BRONCE
Estado: STABLE
Descripción: PROHIBIDO SQLite en el MVP. JSONL simple con hash SHA-256 hacia vector.

Mecánica:

Valor: Reduce consumo de CPU. El caché es texto plano auditable.
Requisitos técnicos: hashlib (stdlib). JSONL append-only. Normalización de texto.
Dependencias: Ninguna nueva.
Invariantes aplicadas: A.1(1), A.1(5)
Puntos de fricción: Ninguno. Transparencia de caché como terapia de confianza.
Reglas de seguridad: Si el nodo es compartido, el caché debe cifrarse en reposo.

SKILL P.08: LA FORJA (EVALUACIÓN DUAL)
---
Medallón: PLATA
Estado: BETA
Descripción: Rito de paso para subir de nivel. Evaluación dual: semántica + heurística.
  Emite Proof of Knowledge firmado con Ed25519.
Mecánica:
  1. TEMPORAL BINDING: Cada sesión de evaluación usa session_nonce derivado de:
     session_nonce = SHA-256(Gold_tip + session_timestamp + topic)
  2. La rúbrica embedding se perturba con nonce_vector:
     rubrica_activa = normalize(rubrica_fija + 0.1 * nonce_vector)
  3. Usuario completa tarea. Sistema compara embedding de respuesta vs rubrica_activa.
  4. Evaluador heurístico O(N): palabras únicas / totales > 0.4, longitud > 500 chars.
  5. BURST DETECTION: Análisis de varianza temporal en ventanas de diversidad léxica.
     Si varianza > BOT_THRESHOLD, alerta de patrón artificial.
  6. Si ambos pasan y no hay burst, genera PoK: JSON con claims (nivel, tema, HLC,
     hash de prueba). Firma con Ed25519. Guarda en Gold.
Valor: El LLM no es juez de su propio examen. La rúbrica es código fijo.
  El PoK es prueba verificable de competencia.
Requisitos técnicos: nomic-embed-text. Cálculo de cosine similarity. Heurística O(N).
  Ed25519 para firma. Temporal Binding + Burst Detection.
Dependencias: B.04
Invariantes aplicadas: A.1(3), A.1(4), A.1(6), A.7, A.8
Puntos de fricción: Evaluación auténtica con anti-trampa técnica.
Reglas de seguridad: Mecanismo de revocación: si se detecta plagio posteriormente,
  el PoK puede ser invalidado. La reputación del protocolo depende de su integridad.
Historial de cambios:
  - V3: Versión original vulnerable a adversarial embeddings y precomputación.
  - V4: Añadidos Temporal Binding, Commitment Protocol y Burst Detection
        (auditoría V3, Sección 3). Estado BETA hasta validación anti-trampa.

SKILL P.19: EL COMPILADOR COMO RÚBRICA
---
Medallón: PLATA
Estado: STABLE
Descripción: Para lenguajes tipados (Rust, C, Go, TypeScript), el mejor parser
  determinista es el compilador mismo. Aurelius no necesita evaluador semántico.
Mecánica:
  1. Usuario recibe misión: 'Escribe una función en Rust que...'
  2. Escribe código en editor de Aurelius.
  3. Sistema guarda snippet en /tmp/aurelius_forge_X.rs.
  4. Ejecuta compilador en sandbox (firejail/nsjail/contenedor ligero) con flags
     de solo-verificación (--noEmit, --crate-type lib).
  5. Si exit code == 0 y sin warnings configurados como errores: pasa.
  6. Si compilador rechaza: La Forja falla y muestra stderr como retroalimentación.
  7. LLM no interviene en evaluación; solo traduce error a lenguaje pedagógico si se solicita.
Valor: Elimina subjetividad de evaluación de código. El lenguaje mismo dicta la verdad.
Requisitos técnicos: Sandbox de compilación (firejail/nsjail). Soporte para rustc,
  tsc, go build, gcc. Parser de exit code y stderr. Timeout de 10s. Sanitización de stderr.
Dependencias: B.04 (Honest Math para timeouts y límites de memoria).
Invariantes aplicadas: A.1(3), A.1(4), A.1(9)
Puntos de fricción: El compilador no negocia. El error es el maestro.
Reglas de seguridad: Sandbox robusto con perfiles restrictivos. Nunca ejecutar código
  del usuario; solo compilar (--noEmit, --crate-type lib). Sanitizar stderr antes de
  mostrarlo (eliminar rutas de archivos internos).
Historial de cambios:
  - V3: Versión original.
  - V4: Añadida sanitización de stderr y enfatizado sandbox obligatorio.
